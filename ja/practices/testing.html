テスト戦略#

テストはカバレッジの数字を稼ぐためではなく、実際の振る舞いを検証するために書く。

テストを追加する前に、どの障害を検出するためのテストかを明確にすること。

優先するのは次の対象である。

  • 中核となるビジネスロジック
  • 重要なユーザーの振る舞い
  • 障害が発生しやすいことが分かっている経路
  • 境界条件
  • エラー処理
  • 例外的な状況
  • 統合の境界

カバレッジの数値は参考になるが、それ自体が目的ではない。目的は、重要な振る舞いが正しく動くと確信できることにある。

フロントエンドの E2E テスト#

フロントエンドプロジェクトでは、可能な範囲で E2E テストを設けること。

E2E テストの対象は次のとおりである。

  • 主要なユーザーフロー
  • 重要なプロダクトの振る舞い
  • 重要な統合の振る舞い

実際の利用に近いテストデータを使うこと。本番に近いデータが有効な場合は、事前に匿名化またはサニタイズし、本番環境の機密情報をテストフィクスチャに絶対に含めないこと。

E2E テストの実行時間は短く保つ。品質ゲートを大幅に遅らせるだけで、それに見合う確信が得られない肥大化した E2E スイートを作らないこと。

Playwright を使うプロジェクトでは、jsPlugins 配列を介して eslint-plugin-playwright を oxlint に読み込むこと。このプラグインは oxlint との適合性テストを公式に受けている。oxlint の JS プラグインサポートは現在アルファ版である。

overrides エントリでルールの適用範囲を Playwright のテストファイルに限定し、アプリケーションコードに適用されないようにすること。

// .oxlintrc.json
{
  "jsPlugins": ["eslint-plugin-playwright"],
  "overrides": [
    {
      "files": ["e2e/**/*.ts"],
      "rules": {
        "playwright/no-networkidle": "error",
        "playwright/no-wait-for-timeout": "warn",
      },
    },
  ],
}

フロントエンドのユニットテスト#

フロントエンドプロジェクトでは、可能な範囲で重要なコンポーネントとロジックにユニットテストを書き、テストの質が高まる場合はサニタイズ済みの現実的なデータを使うこと。

優先するのは次の対象である。

  • 重要なコンポーネントの振る舞い
  • ビジネスロジック
  • 状態遷移
  • データ変換
  • エッジケース
  • エラーが発生する条件

ユニットテストは高速に保つこと。

実装の詳細をそのまま再現するだけのテストを避けること。
