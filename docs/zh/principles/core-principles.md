# 核心工程原则

## 目的

本指南定义面向 AI 辅助快速想法验证与 POC 开发的工程标准。

目标是在快速推进的同时,让项目保持:

* 简单
* 一致
* 可复现
* 易于理解
* 人与 AI agent 都易于维护
* 不易发生意外的架构漂移
* 跨仓库一致

核心原则只有一条:

> **凡是无需作为项目级决策的事项,一律标准化。**

不要在每个项目中反复重新评估包管理器、格式化工具、Lint 工具、任务运行器、提交规范、pre-commit 体系之类的工程基础设施。

产品决策与架构可以因项目而异。

工程工具链不应如此。

## 以验证速度为先

这类项目首先服务于快速想法验证。

不要引入不必要的:

* 抽象
* 分层
* 框架
* 服务
* 基础设施
* 文档
* 流程
* 泛化的扩展性

优先选择能正确解决当前问题的最简连贯实现。

快速开发不等于随意开发。

避免日后制造无谓混乱、或让 AI 辅助开发变得不可靠的决策。

## 减少无谓选择

人和 AI agent 不应反复决策已经标准化的事项。

只要本指南指定了某个工具,该工具即为强制使用,除非用户明确批准例外。

不要仅因下列原因替换标准化工具:

* 另一个工具更流行
* 某个框架推荐了别的工具
* 生成的模板自带别的工具
* AI agent 更熟悉别的工具
* 互联网上的其他项目用了不同的东西

确实存在技术不兼容时,先向用户说明,再变更标准化工具链。

禁止静默替换工具。

## 根因优先,不掩症状

当出现警告、Lint 错误、测试失败、类型错误或其他校验问题时:

1. 弄清该规则或检查保护的是什么。
2. 定位真正的根本原因。
3. 只要合理,就修复底层问题。
4. 理解影响之后,才考虑调整配置。

禁止:

* 盲目改代码直到警告消失
* 仅为让 CI 变绿而禁用规则
* 未理解问题就添加忽略注释
* 削弱测试来换取通过
* 掩盖失败而不是解决失败

若某条规则确实不适合本项目,允许调整其配置,但该调整必须是有意为之且有技术依据。

## 最终原则

本指南的目的不是把流程堆到最多。

它要营造的是一个可预期的工程环境:人和 AI agent 都能快速推进,不必反复解决相同的工具与工作流决策。

当一项选择并不实质依赖产品时:

> **就把它标准化。**

当一项变更影响架构时:

> **就把它显式化。**

当一项校验未通过时:

> **先弄清原因。**

当多种语言并存时:

> **保持它们的边界清晰。**

当 AI agent 参与项目时:

> **压缩它无谓的决策空间,让正确动作成为默认。**
