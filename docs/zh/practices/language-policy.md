# 语言政策

语言边界是项目的一项约束,必须显式对待。

以下三个概念相互独立:

1. 对话语言
2. 源代码语言
3. 产品 / UI 语言

不要由其中任何一个推断另一个。

一个合法的项目配置可能是:

```text
Conversation: Chinese
UI: Japanese
Code: English
```

这些语言必须各自独立、各自地道。

## 代码语言

除刻意包含其他语言的字面值外,所有源代码必须使用标准英语。

以下内容必须用英语书写:

* 变量名
* 函数名
* 方法名
* 类名
* 类型名
* 接口名
* 枚举名
* 模块名
* 文件名
* 目录名
* 代码注释
* 文档字符串(docstring)
* 配置标识符
* 内部符号标识符

禁止在代码标识符或注释中使用非英语语言。

尤其禁止使用:

* 日文假名
* 日语标识符
* 中文标识符
* 拼音标识符
* 日语罗马字标识符

被禁止的标识符包括如下模式:

```text
kokyakuName
shinseiStatus
kehuName
yonghuId
```

改用语义清晰的英语:

```text
customerName
applicationStatus
customerName
userId
```

不要仅为满足 ASCII 要求,就把非英语词汇转写成拉丁字母。

要求的是**标准英语**,而不仅仅是 ASCII。

### 字面值

当非英语文本是刻意设计的字面值内容时,允许使用,包括:

* UI 文案
* 本地化资源
* 面向用户的错误信息
* 包含本地化内容的测试夹具
* 示例用户内容
* 必须保留原始形式的领域数据

字面值不能成为使用非英语变量名或注释的理由。

## 对话语言

使用用户所用的语言自然交流。

对话应当:

* 自然
* 友好
* 清晰
* 地道
* 契合用户的沟通风格

避免不必要的语言混杂。

用中文交流时,不要仅因为实现内部使用英语,就插入英文短语。

涉及以下内容时适合使用英语:

* 代码标识符
* API 名称
* 库名称
* 命令
* 产品名
* 翻译后会降低清晰度的既有技术术语

其余情况用中文自然交流。

同样的原则适用于其他语言。

## 产品与 UI 语言

永远不要仅凭对话语言推断产品语言。

在项目语言尚未写入文档时,实现较重要的面向用户内容之前,先与用户确认:

* UI 主语言
* 需额外支持的语言
* 相关的正式程度或语气要求

将确认后的语言政策记录到项目文档中(参见[必备项目文档](project-documentation.md))。

记录之后照此执行,不要反复询问同一问题。

仅在以下情况重新确认:

* 用户明确变更需求
* 新需求与已记录的政策冲突
* 目标语言确实存在歧义

不要因为用户切换了对话语言,就擅自更改 UI 语言。

## 跨语言质量

当对话、代码、产品三者语言不一致时,要格外用心。

不要跨语言机械照搬措辞。

尤其:

* 不要写出带中文腔的日语。
* 不要把中文句式生硬地套进日语。
* 不要毫无理由地把面向实现的英文,直接插进本应自然的中文对话。
* 不要让同一领域概念在 UI 各处译法不一。
* 不要从中文开发对话推断日语 UI 用语。
* 不要从英文源代码标识符推断中文 UI 用语。

面向用户的 UI 文案应优先保证:

1. 符合目标语言的规范用法
2. 语法正确
3. 含义清晰
4. 正式程度得当
5. 易于理解
6. 易于使用
7. 与产品其余部分保持一致

UI 文案应当专业、自然,而不是充满直译或机翻的味道。

重要术语或语气拿不准时,询问用户,不要自行发明惯例。
