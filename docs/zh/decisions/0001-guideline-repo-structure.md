# ADR-0001:指南仓库结构与国际化模型

- **状态**:已接受
- **日期**:2026-08-15

## 背景

这套工程指南原本是一个约 1300 行的 Markdown 单体文件。它太长,人类难以可靠地编辑,AI Agent 也无法按需选择性加载。团队在中、英、日三种语言之间协作;每个成员都必须能用自己最擅长的语言改进指南,而不必分叉内容。

## 决策

- 内容存放于三棵同构语言树:`docs/en/**`、`docs/zh/**`、`docs/ja/**`。每份文档都是只关注单一主题的小文件(正文不超过 300 行)。
- **不设基准语言**。任何语言都可以先行编辑;front matter 记录 `version`、`source-lang` 与 `status`,同一文档的三份语言文件必须一致,此外每个文件还带有规范化正文的 `digest`。另外两种语言以母语级重写,在同一次变更中落地。
- 面向机器的根目录文件(`AGENTS.md`、`PORTAL.md`、`GLOSSARY.md`、`README.md`、`templates/**`、`tools/**`)仅使用英文。
- 零依赖校验器(`tools/check-docs.ts`)强制执行树同构、front matter 模式、三语一致性、digest、标题层级对齐、体积上限与 portal 覆盖检查。CI 与预提交钩子运行同一套检查。

## 考虑过的替代方案

### 单棵目录树内按后缀区分文件(`mise.en.md`、`mise.zh.md` 等)

- 优点:各译文物理相邻,便于对照评审 diff。
- 缺点:每个目录的文件数量变为三倍;浏览体验嘈杂;与整洁的仓库布局目标相悖。

### 每份文档一个文件夹(`docs/toolchain/mise/{en,zh,ja}.md`)

- 优点:三份语言文件同居一处;目录数量不变。
- 缺点:嵌套更深;文件名失去语义;没有单一语言的沉浸式阅读路径。

### 以基准语言加翻译流水线

- 优点:版本模型简单;由工具判定内容是否过期。
- 缺点:非基准语言的编辑沦为二等公民;与"任何成员都能用自己的语言改进内容"的需求冲突。

## 后果

- 每次内容编辑至少触及三个文件;Agent 将其作为常规协议处理(见 `AGENTS.md`)。
- 校验器必须保持零依赖且快速,否则会被绕过。
- 强制的是标题层级对齐,而非完全的结构一致,因此各语言的标题可以按本语言习惯措辞。

## 复审触发条件

- 文档数量增长到约 60 个 id 以上。
- 团队构成或工作语言发生变化。
- 校验器成为编辑工作的日常阻碍。
