# ADR-0001: ガイドラインリポジトリの構造と i18n モデル

- **ステータス**: accepted
- **日付**: 2026-08-15

## 背景

エンジニアリングガイドラインは従来、約 1300 行の単一 Markdown ファイルであった。人間が確実に編集するには長すぎ、AI エージェントが必要な部分だけを読み込むことも不可能であった。チームは中国語・英語・日本語で作業しており、全メンバーが内容を fork することなく、各自が最も得意な言語でガイドラインを改善できなければならない。

## 決定

- コンテンツは `docs/en/**`、`docs/zh/**`、`docs/ja/**` の 3 つの同型言語ツリーで管理する。各ドキュメントは単一関心事の小さなファイルとし、本文は 300 行までに制限する。
- **canonical となる言語は存在しない**。どの言語から編集してもよい。front matter には `version`、`source-lang`、`status` を記録し、これらはトリオ内で同一でなければならない。加えて、正規化した本文の `digest` をファイルごとに持つ。残る 2 言語は、同じ変更の中で母語品質のリライトとして反映する。
- 機械が相手となるルートファイル(`AGENTS.md`、`PORTAL.md`、`GLOSSARY.md`、`README.md`、`templates/**`、`tools/**`)は英語のみとする。
- ゼロ依存のバリデーター(`tools/check-docs.ts`)が、ツリーの同型性、front matter スキーマ、トリオの一貫性、digest、見出しレベルの一致、行数上限、ポータルカバレッジを強制する。CI とプリコミットフックも同じチェックを実行する。

## 検討した代替案

### 1 つのツリーにサフィックス付きで並べる方式(`mise.en.md`、`mise.zh.md`、...)

- 利点: 翻訳同士が物理的に隣接し、レビューでの diff 比較が容易である。
- 欠点: 全ディレクトリでファイル数が 3 倍になり、閲覧のノイズが増える。クリーンなリポジトリレイアウトという目標に反する。

### ドキュメントごとにフォルダーを分ける方式(`docs/toolchain/mise/{en,zh,ja}.md`)

- 利点: トリオが同じ場所に集まり、ディレクトリ数は増えない。
- 欠点: ネストが深くなり、ファイル名から意味が失われる。単一言語でまとめて読む経路が得られない。

### canonical 言語と翻訳パイプラインの方式

- 利点: バージョンモデルが自明であり、ツールが内容の古さを判定できる。
- 欠点: canonical 言語以外での編集が二級扱いになる。誰でも自分の言語で内容を改善できるという要件と競合する。

## 帰結

- コンテンツの編集は必ず 3 つ以上のファイルに触れる。エージェントはこれを定型プロトコルとして扱う(`AGENTS.md` を参照)。
- バリデーターはゼロ依存かつ高速であり続けなければならない。さもなければ、迂回されてしまう。
- 強制するのは見出しレベルの一致であって、構造の完全な同一性ではない。そのため、各言語は見出しを自然な表現で書ける。

## 再検討のトリガー

- ドキュメント数が約 60 id を超えて増え続けたとき。
- チーム構成または作業言語が変わったとき。
- バリデーターが編集における日常的な障害になったとき。
