# 核心工程原则

## 目的

本指南为 AI 辅助的快速想法验证与 POC 开发定义工程标准。

目标是在快速推进的同时，让项目保持：

- 简单
- 一致
- 可复现
- 易于理解
- 人和 AI Agent 都易于维护
- 不易发生意外的架构漂移
- 跨仓库一致

核心原则只有一条：

> **凡是无需作为项目级决策的事项，一律标准化。**

不要在每个项目里重新评估包管理器、格式化工具、Lint 工具、任务运行器、提交规范、预提交体系等工程基础设施。

产品决策与架构可以因项目而异。

工程工具链不应因项目而异。

## 以验证速度为先

这类项目首先服务于快速想法验证。

不要引入不必要的：

- 抽象
- 分层
- 框架
- 服务
- 基础设施
- 文档
- 流程
- 泛化的扩展性

优先采用最简且连贯的实现，正确解决当前问题。

快速开发不等于随意开发。

避免做出日后制造无谓混乱或让 AI 辅助开发变得不可靠的决策。

## 减少无谓选择

对已经标准化的事项，人和 AI Agent 不要反复做决策。

本指南指定了某个工具时，该工具即强制使用，除非用户明确批准例外。

不要仅因下列原因替换标准化工具：

- 另一个工具更流行
- 某个框架推荐了别的工具
- 生成的模板自带别的工具
- AI Agent 更熟悉别的工具
- 互联网上的其他项目用了不同的东西

确实存在技术不兼容时，先向用户说明，再变更标准化工具链。

禁止静默替换工具。

## 优先选择主流且经过充分验证的方案

AI Agent 依据训练数据生成代码，而不是实时查阅文档。

崭新或小众的版本与技术栈在训练数据中覆盖不足，会加剧幻觉导致的破坏：崩溃、错误的 API、行为不一致。

因此，默认选择主流且经过充分验证的方案：

- 运行时跟随 LTS 或成熟版本线：默认 Node.js Active LTS，机器学习工作固定 Python 3.12。
- 库优先选择主流、文档充分的选项，而非崭新或冷门的替代品。
- 前沿大版本、小众框架和小众运行时（例如以 Bun 为底座的技术栈）必须获得用户明确批准并记录理由。
- 在默认决策中，兼容性优先于边际性能提升。

稳定性优先于边际收益。

把模型的知识覆盖度当作选型标准，与基准测试和功能清单同等看待。

## 根因优先，不掩症状

当出现警告、Lint 错误、测试失败、类型错误或其他校验问题时：

1. 弄清该规则或检查保护的是什么。
2. 定位实际的根本原因。
3. 只要合理，就修复底层问题。
4. 理解影响之后，再考虑调整配置。

禁止：

- 盲目改代码直到警告消失
- 仅为让 CI 变绿而禁用规则
- 未理解问题就添加忽略注释
- 削弱测试来换取通过
- 掩盖失败而不是解决失败

若某条规则确实不适合本项目，可以调整其配置，但调整必须是有意为之且有技术依据。

## 最终原则

本指南的目的不是让流程越多越好。

它要营造一个可预期的工程环境：人和 AI Agent 都能快速推进，不必反复处理相同的工具与工作流决策。

当一项选择与产品实质无关时：

> **就把它标准化。**

当版本或技术栈成熟度不同时：

> **选经过充分验证的那个。**

当一项变更影响架构时：

> **就把它显式化。**

当一项校验未通过时：

> **先弄清原因。**

当多种语言并存时：

> **保持它们的边界清晰。**

当 AI Agent 参与项目时：

> **压缩它无谓的决策空间，让正确动作成为默认。**
