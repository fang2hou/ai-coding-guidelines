# 核心工程原则

## 目的

本指南规定了在 AI 辅助下快速验证想法和开发 POC 的工程标准。

目标是让项目在快速推进的同时保持：

- 简单
- 一致
- 可复现
- 易于理解
- 便于人和 AI Agent 维护
- 不易出现意外的架构漂移
- 跨仓库保持一致

核心原则是：

> **凡是不需要项目单独决策的事项，一律标准化。**

不要让每个项目反复决定包管理器、格式化工具、Lint 工具、任务运行器、提交规范、预提交系统等工程基础设施。

产品决策与架构可以因项目而异。

工程工具链不应因项目而异。

## 以验证速度为先

这类项目主要用于快速验证想法。

不要引入不必要的：

- 抽象
- 分层
- 框架
- 服务
- 基础设施
- 文档
- 流程
- 通用扩展能力

优先选择能正确解决当前问题的最简单、自洽的实现。

快速开发不等于随意开发。

避免做出会在日后造成不必要的混乱，或使 AI 辅助开发变得不可靠的决策。

## 减少无谓选择

人和 AI Agent 不要反复决定已经标准化的事项。

本指南指定某项工具后，除非用户明确批准例外情况，否则必须使用该工具。

不要仅因下列原因替换标准化工具：

- 另一个工具更流行
- 某个框架推荐了别的工具
- 生成的模板使用了别的工具
- AI Agent 更熟悉别的工具
- 互联网上的其他项目使用了不同的工具

如果确实存在技术不兼容，先向用户说明，再变更标准化工具链。

禁止静默替换工具。

## 优先选择主流且经过充分验证的方案

AI Agent 根据训练数据生成代码，而不是查阅实时文档。

新近或小众的版本与技术栈在训练数据中的覆盖较少，因此更容易因幻觉而导致以下问题：崩溃、API 调用错误、行为不一致。

因此，默认选择主流且经过充分验证的方案：

- 运行时采用 LTS 或成熟版本线：默认使用 Node.js Active LTS；机器学习工作使用 Python 3.12。
- 库优先选用主流、文档充分的方案，而不是新近或冷门的替代品。
- 最前沿的主版本、小众框架和小众运行时（例如以 Bun 为底座的技术栈）必须获得用户明确批准，并在项目 ADR 中记录理由。
- 在默认决策中，兼容性优先于边际性能提升。

稳定性优先于边际收益。

将模型知识的覆盖度作为选型标准，与基准测试和功能清单一并考虑。

## 优先解决根本原因，不要掩盖症状

当出现警告、Lint 错误、测试失败、类型错误或其他校验问题时：

1. 弄清该规则或检查要保护什么。
2. 找出真正的根本原因。
3. 只要可行，就修复底层问题。
4. 先了解影响，再考虑调整配置。

禁止：

- 盲目修改代码直到警告消失
- 仅为使 CI 通过而禁用规则
- 未理解问题就添加忽略注释
- 为了让测试通过而降低测试强度
- 掩盖失败而不去解决问题

若某条规则确实不适合本项目，可以调整其配置，但必须出于明确意图，并有技术依据。

## 最终原则

本指南的目的不是一味增加流程。

它旨在营造可预期的工程环境，让人和 AI Agent 都能快速推进，不必反复作出相同的工具和工作流选择。

当某项选择与产品没有实质关系时：

> **就把它标准化。**

当版本或技术栈成熟度不同时：

> **优先选择经过充分验证的版本或技术栈。**

当一项变更影响架构时：

> **明确说明这项变更。**

当一项校验未通过时：

> **先弄清原因。**

当多种语言并存时：

> **保持它们的边界清晰。**

当 AI Agent 参与项目时：

> **缩小其不必要的决策空间，让正确做法成为默认选项。**
