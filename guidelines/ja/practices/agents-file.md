# AGENTS.md の執筆

`AGENTS.md` はリポジトリにおけるエージェントの入口であり、コードを書く前に読み込む作業コンテキストである。エージェントハーネスはこれを最初に読み込み、保持できる指示コンテキストにも上限がある。各行に、割くスペースに見合う価値を持たせること。

テンプレート：[project-agents.template.md](../../../templates/project-agents.template.md)

## 必須要件

すべてのプロジェクトは、リポジトリのルートに `AGENTS.md` を 1 つ置くこと。

正式なファイル名は `AGENTS.md` である。同じルールを `CLAUDE.md` などの互換性のあるファイル名に複製しないこと。指示ファイルを複製すると内容が食い違い、コンテキスト予算を二重に消費する。

## 適切な記述先

指針は種類に応じて適切な場所に置くこと。

| 内容                                           | 記述先                                                       |
| ---------------------------------------------- | ------------------------------------------------------------ |
| 常に適用するコマンド、規約、境界               | `AGENTS.md`                                                  |
| プロダクトの背景、導入説明、スクリーンショット | `README.md`                                                  |
| 開発ワークフローとツールチェーンの詳細         | `DEVELOPMENT.md`                                             |
| プルリクエスト、レビュー、検証の要件           | `CONTRIBUTING.md`                                            |
| アーキテクチャの不変条件                       | `ARCHITECTURE.md`                                            |
| 特定のワークフローにだけ必要な手順             | 別ドキュメントまたはエージェントスキル（リンクを付けて参照） |
| エージェントツールの設定、既定モデル、自律度   | 各ツールの設定ファイル                                       |

運用手順書や長い参照ドキュメント、個別タスクのメモを `AGENTS.md` に貼り付けないこと。信頼できる唯一の情報源にリンクすること。

## 構成

冒頭に、プロジェクトの目的と対象を 1 文で示すこと。その後は、エージェントが必要とする順に、テンプレートに沿って節を並べること。

1. コマンド――セットアップ、実行、単一テスト、テスト、lint、型チェック、ビルド、再生成、全体検証の正確なコマンドを記載する。プロジェクトにない項目は省くこと。
2. エンジニアリング標準――共有ガイドラインと、プロジェクト固有の例外。
3. 構成――トップレベルのディレクトリごとに 1 行で、主要モジュールを示す。
4. 境界――必ず行うこと、決して行わないこと、事前に確認すること。
5. 確定した言語ポリシー――[言語ポリシー](language-policy.md)を参照する。
6. プロジェクト固有の取り決め――コードからは推測できない判断。
7. `DEVELOPMENT.md`、`CONTRIBUTING.md`、`ARCHITECTURE.md` への詳細リンク。

コマンドを最初に置くこと。エージェントが最初の 1 分で必要とするのはコマンドだからである。対象を絞ったコマンドと、全体検証のコマンドを両方示すこと。1 行の変更には対象を絞ったテストコマンドを、コミット前には `mise run check` を示すこと。そうすれば、エージェントが既定で最も重いコマンドを選ばずに済む。

## 検証可能なルール

すべてのルールは、エージェントが実行でき、レビュアーが確認できる行動として示すこと。コマンド、パス、条件を具体的に記すこと。

検証可能な例：

```markdown
- `src/auth/` 配下を変更したら `mise run test -- src/auth/token.test.ts` を実行する。
- `src/generated/` 配下は手で編集しない。`mise run codegen` で再生成する。
- 依存関係の追加や `ARCHITECTURE.md` の不変条件の変更は、事前に確認する。
```

検証できず、役に立たない例：

```markdown
- 認証コードは慎重に扱う。
- すべてが動くことを確認する。
- ベストプラクティスに従う。
```

## ネストしたファイル

まずルートに 1 ファイルだけ置くこと。ネストした `AGENTS.md` を追加するのは、そのディレクトリツリーに実質的な違いがある場合だけとする。

- 別のパッケージマネージャー、テストランナー、ランタイムを使用する場合。
- 手で編集せず、再生成する必要がある生成コードを含む場合。
- マイグレーションやデプロイなど、追加の承認が必要な場合。
- 他の場所には適用されない UI やデザインシステムのルールがある場合。

ネストしたファイルには固有の差分だけを記載し、それ以外はルートに委ねること。ルートのルールをネストしたファイルで繰り返してはならない。

## ファイルサイズ

ファイルは各タスクの開始時に読み込まれるため、サイズが大きいほど繰り返しコストが増える。

- 最も重要なルールを先頭に置くこと。
- 詳細ドキュメントを複製せず、リンクで案内すること。
- 文章で説明するより、機械的なチェックを優先すること。リンター、prek、CI がすでに強制しているルールを改めて記載しないこと。
- サブシステム固有の指針は、ルートを膨らませず、ネストしたファイルへ移すこと。

ルートファイルは一読で全体を把握できる状態に保つこと。そうでなくなった場合に必要なのは、リンクによる振り分けと削除であり、記述の圧縮ではない。

## 記載しない内容

- シークレット、トークン、内部ホスト名。
- リポジトリ内にすでに存在するドキュメントの複製。
- 網羅的なディレクトリ一覧。次のリファクタリングですぐに古くなる。
- Issue やプルリクエストに記載すべき一時的なタスクメモ。
- 検証を一律に省略させる指示。

## 最新状態の維持

コマンド、構成、境界、取り決めを変更するときは、同じ変更で `AGENTS.md` も更新すること。

古い指示は、指示がないよりも悪い。エージェントはそれを疑わずに実行し、誰も求めていない変更を生み出す。
