# AGENTS.md の書き方

`AGENTS.md` はリポジトリにおけるエージェントの入口であり、エージェントがコードを書き始める前に読み込む作業コンテキストである。エージェントツールは作業開始前にこれを読み込み、保持できる指示コンテキストには上限があるため、1 行ごとにその場所を占めるだけの価値が必要になる。

テンプレート：[project-agents.template.md](../../../templates/project-agents.template.md)

## 必須要件

すべてのプロジェクトは、リポジトリのルートに `AGENTS.md` を 1 つ置くこと。

正式なファイル名は `AGENTS.md` である。同じルールを `CLAUDE.md` などの互換ファイル名に複製しないこと。指示ファイルを複製すると、内容が互いにずれ、コンテキスト予算を二重に消費する。

## 記述先を選ぶ

指針の種類ごとに、置くべき場所へ振り分ける。

| 内容                                           | 記述先                                                   |
| ---------------------------------------------- | -------------------------------------------------------- |
| 常時適用のコマンド、取り決め、境界             | `AGENTS.md`                                              |
| プロダクトの背景、導入説明、スクリーンショット | `README.md`                                              |
| 開発ワークフローとツールチェーンの詳細         | `DEVELOPMENT.md`                                         |
| プルリクエスト、レビュー、必須の検証           | `CONTRIBUTING.md`                                        |
| アーキテクチャの不変条件                       | `ARCHITECTURE.md`                                        |
| 特定のワークフローでしか使わない手順           | 別ドキュメントまたはエージェントの skill（リンクで参照） |
| エージェントツールの設定、既定モデル、自律度   | そのツール自身の設定ファイル                             |

運用手順書、長い参照ドキュメント、個別タスクのメモを `AGENTS.md` に貼り付けないこと。信頼できる唯一の情報源へリンクする。

## 構成

冒頭に、このプロジェクトが何であり誰のためのものかを 1 文で書く。その後は、エージェントが最初に必要とする順に、テンプレートに沿って節を並べる。

1. コマンド——セットアップ、実行、単一テスト、テスト、lint、型チェック、ビルド、再生成、全体検証の正確なコマンド。プロジェクトに存在しない行は削除する。
2. エンジニアリング標準——共有ガイドラインと、プロジェクト固有の例外。
3. コードマップ——トップレベルのディレクトリごとに 1 行、主要モジュールを名指しする。
4. 境界——必ずやること / 絶対にやらないこと / 事前に確認すること。
5. 確定した言語ポリシー——[言語ポリシー](language-policy.md)を参照。
6. プロジェクト固有の取り決め——コードから推測できない判断。
7. `DEVELOPMENT.md`、`CONTRIBUTING.md`、`ARCHITECTURE.md` への詳細リンク。

コマンドを最初に置く。エージェントが最初の 1 分で必要とするのはコマンドだからである。絞ったコマンドと全体ゲートの両方を示すこと。1 行の変更には対象を絞ったテストコマンド、コミット前には `mise run check` とすれば、エージェントが既定で最も重いコマンドを選ぶことはなくなる。

## 検証できるルールを書く

すべてのルールは、エージェントが実行でき、レビュアーが確認できる行動を示さなければならない。コマンド、パス、条件を名指しする。

検証できる例：

```markdown
- `src/auth/` 配下を変更したら `mise run test -- src/auth/token.test.ts` を実行する。
- `src/generated/` 配下は手で編集しない。`mise run codegen` で再生成する。
- 依存関係の追加や `ARCHITECTURE.md` の不変条件の変更は、事前に確認する。
```

検証できず、役に立たない例：

```markdown
- 認証コードは慎重に扱う。
- すべてが動くことを確認する。
- ベストプラクティスに従う。
```

## ネストしたファイル

まずルートの 1 ファイルから始める。ネストした `AGENTS.md` を追加するのは、そのディレクトリツリーが実際に異なる場合だけとする。

- 別のパッケージマネージャー、テストランナー、ランタイムを使っている。
- 手で編集せず再生成すべき生成コードを含む。
- マイグレーションやデプロイなど、追加の承認要件を伴う。
- 他の場所には当てはまらない UI やデザインシステムのルールがある。

ネストしたファイルには差分だけを書き、それ以外はルートに委ねる。ルートのルールをネストしたファイルで繰り返さないこと。

## 小さく保つ

ファイル全体がタスクごとに読み込まれるため、サイズは繰り返し支払うコストになる。

- 最も重要なルールを先頭に置く。
- 詳細ドキュメントは複製せず、リンクで誘導する。
- 文章よりも機械的なチェックを優先する。リンター、prek、CI が既に強制しているルールを書き直す必要はない。
- サブシステム固有の指針は、ルートを膨らませるのではなくネストしたファイルへ移す。

ルートのファイルは一読で見渡せる状態に保つこと。そうでなくなったら、直すべきはリンクへの振り分けと削除であり、記述の圧縮ではない。

## 書いてはいけない内容

- シークレット、トークン、内部ホスト名。
- リポジトリ内に既に存在するドキュメントの写し。
- 網羅的なディレクトリ一覧。次のリファクタリングで古くなる。
- Issue やプルリクエストに書くべき一時的なタスクメモ。
- 検証を一律に省略させる指示。

## 最新の状態に保つ

コマンド、コードマップ、境界、取り決めを変えるときは、同じ変更のなかで `AGENTS.md` も更新すること。

古い指示は、書かれていない場合よりも悪い。エージェントはそれを疑わずに実行し、誰も求めていない変更を出してくる。
