# 必須のプロジェクトドキュメント

すべてのプロジェクトは、`AGENTS.md`、`README.md`、`DEVELOPMENT.md`、`CONTRIBUTING.md` を維持しなければならない。重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` も必須とする。出発点として、`templates/` 配下のテンプレートを使用すること。

ドキュメントの役割分担は [Diátaxis](https://diataxis.fr/) に基づく。`README.md` は人間の読者にプロジェクトを紹介して使い始め方を示し、`DEVELOPMENT.md` と `CONTRIBUTING.md` は利用方法と参考資料、`ARCHITECTURE.md` は解説、`AGENTS.md` はエージェント向けの参考資料を担う。1 つのドキュメントが担うモードは 1 つとし、別のモードの内容が必要になったら、それを担うドキュメントへリンクすること。1 つのファイルに混ぜないこと。

## AGENTS.md

すべてのプロジェクトは、リポジトリのルートに `AGENTS.md` を置かなければならない。

これはエージェント向けの入口である。コマンド、エンジニアリング標準、リポジトリの構成、境界、確定した言語ポリシー、プロジェクトの規約を記述する。

書き方のルール（記載内容の振り分け、セクション順、長さの上限、ネストしたファイル）は、[AGENTS.md の執筆](agents-file.md)で定める。

テンプレート：[project-agents.template.md](../../../templates/project-agents.template.md)

## README.md

すべてのプロジェクトに `README.md` を含めること。

### 読者と役割

`README.md` は人間の読者に向けて書く。プロジェクトの概要、できること、使い方や動かし方を簡潔に伝えることが目的である。チュートリアル、内部向け参考資料、長い背景解説を重複して載せず、単体でプロジェクトの入口として機能させること。

`README.md` をリポジトリ内のファイル案内ページや、「目的 → 読むドキュメント」形式の索引表にしてはならない。現在の AI コーディングエージェントは `AGENTS.md` や `docs/` を自動で検出し、リポジトリ構成や内部ドキュメントへのリンクもすでに `AGENTS.md` にまとまっている。

エージェント向けのルール（エンジニアリング標準、[言語ポリシー](language-policy.md)で確定したプロダクト/UI の言語ポリシー、プロジェクト規約）は `AGENTS.md` に記録し、`README.md` には記載しないこと。

### 構成とレイアウト

本文はリポジトリのディレクトリ構成ではなく、人間の読者が最初に必要とする情報の順に並べる。独立した Why セクションは設けず、次の順序に従うこと。

- **冒頭のヒーローブロック**：`<div align="center">` で中央揃えにし、任意のロゴやバナー画像、1 つだけの `# プロジェクト名` 見出し（ロゴにプロジェクト名が含まれる場合は省略）、プロジェクトの内容と対象を一文で示すタグライン、任意のナビゲーションリンク行、`flat-square` スタイル（`style=flat-square`）の簡潔なステータスバッジを順に配置する。
- **概要**：プロジェクトが何を行い、どんな課題を解決するかを平易な 1〜3 文で述べる。スコープの制約や開発ステータスは、読者の時間を節約できる場合に限り記す。
- **ビジュアルプレビュー（任意）**：UI、CLI 出力、生成物など視覚的に示せる対象がある場合は、概要の直後にスクリーンショットまたは短い GIF を置く。
- **利用者向けの導入と使い方**：エンドユーザー向けの手順とコントリビューター向けの開発環境構築を明確に分ける。インストール可能なプログラム、CLI、パッケージ、フォントなどのダウンロード配布物では、`## 📦 Installation`（または `## 📦 Download & Install`）で入手方法を示し、続けて `## 🚀 Usage` で代表的な 2〜3 の使い方を期待出力付きで示す。エンドユーザーへ配布しない開発専用リポジトリでは `Installation` を省き、`## 🚀 Quick Start` とする。
- **任意の紹介セクション**：プロジェクトに本当に必要なセクションだけを、読者に最も伝えたい順に並べる。
  - `Features`：プロジェクトの機能を飾らず説明する。内容が多い場合は番号付きの ``### `1` `` / ``### `2` `` サブセクションで各 1〜2 文にまとめ、簡潔なプロジェクトでは 2 列の表または自然な文の箇条書きを使う。
  - `Concepts`：既存の代替案とは異なる独自の設計思想や切り口を持つプロジェクトでのみ置く。
  - `Performance`：性能最適化や性能が重要な用途を主眼とするプロジェクトでのみ置く。性能の主張を一文で述べ、裏付けとなる図表、計測環境（ハードウェア、ランタイムバージョン、計測日）、再現手順へのリンクを添える。数値の裏付けがない主張は書かない。
  - `Experiments`：実験的な機能を提供している場合にのみ置く。
- **ローカル開発**：リポジトリ開発者向けのローカル構築手順（`mise install`、`mise run dev`、必要な環境変数、外部サービス）は独立した `## 🛠️ Development` セクションにまとめ、利用者向けの `Installation` や `Usage` に混ぜない。
- **コントリビュート**：個人プロジェクトではない場合に限り簡潔な `## 🤝 Contributing` セクションを置き、`DEVELOPMENT.md`、`CONTRIBUTING.md`、および存在する場合は `ARCHITECTURE.md` へリンクする。個人プロジェクトか共同プロジェクトか判断できない場合は、追加する前にユーザーへ確認すること。
- **ライセンス**：`## 📄 License` の直下に `MIT` のように SPDX 識別子を直接書く（必要なら `LICENSE` ファイルへ直接リンクする）。`MIT — see LICENSE` のような冗長な前置きは書かないこと。

長い補助情報（プラットフォーム別の手順、環境変数の一覧、応用例、トラブルシューティング）は `<details>` ブロックに折りたたむ。`<summary>` は数語で内容を示し、Markdown が正しく描画されるよう直後に空行を 1 つ入れる。冒頭、利用者向けの主要コマンド、ライセンスは折りたたまないこと。

### AI エージェント向けの案内

`README.md` に定型的な AI 引き継ぎプロンプト（「以下の文をエージェントに貼り付けて `AGENTS.md` を読ませる」など）を載せてはならない。

標準的なプロジェクトではエージェントが自動で `AGENTS.md` を読むため、`README.md` から AI 向けの案内自体を省く。インストール可能なエージェントスキル、MCP サーバー、独自のルーティングファイルなど、そのプロジェクト固有の AI 入口や自明でないワークフローがある場合に限り、実際の導入手順だけを簡潔に記すこと。

### 見出し、書式、トーン

Markdown の見出し階層を明快に保つ。最上位の `#` は冒頭のプロジェクト名に最大 1 回だけ使い（ロゴにプロジェクト名が含まれる場合は省く）、主要セクションに `##`、サブセクションに `###` を使う。複数の H1 見出し、シェアボタン行、宣伝用のスローガンは使わないこと。

すべての `##` 主要セクション見出しの先頭には、意味に合った絵文字を 1 つ付ける。標準の `##` セクションでは、導入・ダウンロードに 📦（`Installation` / `Download & Install`）、使い方・開始手順に 🚀（`Usage` / `Quick Start`）、機能に ✨（`Features`）、概念に 💡（`Concepts`）、性能に ⚡（`Performance`）、実験に 🧪（`Experiments`）、ローカル開発に 🛠️（`Development`）、コントリビュートに 🤝（`Contributing`）、ライセンスに 📄（`License`）を使う。番号付きの ``### `1` `` / ``### `2` `` や簡潔なプレーンテキストの方が収まりが良い場合、`###` 見出しに無理に絵文字を付けない。プロジェクト名の `#` 見出しと本文には絵文字を使わないこと。

次の書式パターンは禁止とする。

- リンクバーの区切りに `·`（中点・インターパンク）を使ってはならない。代わりに `|` または個別のバッジを使うこと。

```markdown
<!-- 避ける -->
[Docs](...) · [Changelog](...)
[English](...) · [中文](...) · [日本語](...)

<!-- 代わりに使う -->
[Docs](...) | [Changelog](...)
[English](...) | [中文](...) | [日本語](...)
```

- `- **項目名** — 説明` という太字とエムダッシュを組み合わせた箇条書きの定型を使ってはならない。README 全体でもエムダッシュ（`—`）の使用は最小限に抑え、読点、コロン、括弧、通常の文、`###` サブセクション、2 列の表で表現すること。

文体は実用的かつ率直に保つ。

- 基本的な機能も含め、プロジェクトが実際に行うことを事実に即して記述する。「競合との違い」を誇張する宣伝文句や、根拠のない美辞麗句（`powerful`、`seamless`、`modern-design`、`revolutionary`、`easy`、`simple`、`簡単`、`手軽`、`シームレス`、`革新的`、`強力` など）は避けること。
- 段落は 1〜3 文に収め、コピーして使うコマンドはコードブロックに置く。列挙は長い文章にせず、リストか表で示す。
- 目次は、README が数画面を超える長さになった場合にのみ追加する。

### メンテナンス

日常の更新で `README.md` を頻繁に書き換えずに済む構成を保つ。ドキュメント、ルール、ファイルの正確な件数や、コマンド出力に含まれる具体的な件数文字列など、項目や言語を増やすたびに陳腐化する数値や内部識別子は書かないこと。`README.md` の更新は、大きな仕様変更、セットアップや使い方の変更、節目のリファクタリングにとどめる。

古い README は無いより悪い。読者を誤った手順へ導いてしまうからである。セットアップ、使い方、対象範囲が変わるときは、同じ変更の中で `README.md` も更新すること。開発が停滞または停止した場合は、冒頭で明示すること。

テンプレート：[README.template.md](../../../templates/README.template.md)

## DEVELOPMENT.md

すべてのプロジェクトに `DEVELOPMENT.md` を含めること。

開発ワークフローを手順に沿って説明し、その後にコマンドと設定の参考資料を置くこと。

次の内容を記載すること。

- 開発ワークフロー
- ツールチェーン
- よく使う mise タスク
- コーディング規約
- テストワークフロー
- ローカル環境のセットアップ
- 検証ワークフロー
- 必要に応じたデプロイワークフロー

人間と AI エージェントの双方が、開発の進め方を理解できるようにすること。

テンプレート：[DEVELOPMENT.template.md](../../../templates/DEVELOPMENT.template.md)

## CONTRIBUTING.md

すべてのプロジェクトに `CONTRIBUTING.md` を含めること。

このドキュメントは、変更を送ってからマージされるまでの手順を順に示す。背景解説の長文は書かないこと。

次の内容を文書化すること。

- コントリビューションにあたっての要件
- 必要に応じた Issue のワークフロー
- プルリクエストのワークフロー
- レビュー要件
- 必須の検証
- コミット規約

すべてのプルリクエストの説明文には、次の内容を明確に含めること。

- 変更の目的
- 変更の影響
- 関連する文脈や背景
- 潜在的なリスクや懸念
- 実施したテストまたは検証

GitHub のプルリクエストテンプレートは、これらの要件との同期を保つこと。

テンプレート：[CONTRIBUTING.template.md](../../../templates/CONTRIBUTING.template.md)

## ARCHITECTURE.md

重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` を維持すること。

内容は短く実用的に保つ。簡潔な概要、大まかなコード構成（モジュール名だけを示し、個別ファイルにはリンクしない）、アーキテクチャの不変条件を記載する。

この文書の役割は、境界を設けた理由を説明してアーキテクチャの意図しない崩れを防ぐことであり、網羅的なリファレンスや抽象的な理論書にすることではない。

不変条件と ADR の運用は、[アーキテクチャガバナンス](architecture-governance.md)で定める。

テンプレート：[ARCHITECTURE.template.md](../../../templates/ARCHITECTURE.template.md)
