# 必須のプロジェクトドキュメント

すべてのプロジェクトは、`AGENTS.md`、`README.md`、`DEVELOPMENT.md`、`CONTRIBUTING.md` を維持しなければならない。重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` も必須とする。出発点として、`templates/` 配下のテンプレートを使用すること。

ドキュメントの役割分担は [Diátaxis](https://diataxis.fr/) に基づく。README は読者を導き、適切なドキュメントへ案内する。`DEVELOPMENT.md` と `CONTRIBUTING.md` は利用方法と参考資料、`ARCHITECTURE.md` は解説、`AGENTS.md` はエージェント向けの参考資料を担う。1 つのドキュメントが担うモードは 1 つとし、別のモードの内容が必要になったら、それを担うドキュメントへリンクすること。1 つのファイルに混ぜないこと。

## AGENTS.md

すべてのプロジェクトは、リポジトリのルートに `AGENTS.md` を置かなければならない。

これはエージェント向けの入口である。コマンド、エンジニアリング標準、リポジトリの構成、境界、確定した言語ポリシー、プロジェクトの規約を記述する。

書き方のルール（記載場所の選択、セクションの順序、サイズ、ネストされたファイル）は、[AGENTS.md の記述規則](agents-file.md)で定める。

テンプレート：[project-agents.template.md](../../../templates/project-agents.template.md)

## README.md

すべてのプロジェクトに `README.md` を含めること。

README はプロジェクトの表玄関であり、読者がまず流し読みすることを前提に書く。最初の画面で、プロジェクトが何であるか、どんな課題を解決するか、どう動かすかを示す。読者を導き、適切なドキュメントへ案内するのが README の役割であり、チュートリアル、仕様の羅列、背景の解説は詳細ドキュメントが担う。エージェント向けのルール（エンジニアリング標準、確定した言語ポリシー、プロジェクトの規約）は `AGENTS.md` に記述する（`templates/project-agents.template.md` を参照）。README は、コピー可能な指示文によってリポジトリをエージェントに引き渡す。

本文は、リポジトリのディレクトリ構成ではなく読者のタスクに沿って構成する。Why セクションは単独に設けず、次の順序に従うこと。

- 識別ブロック：プロジェクト名、内容と対象者を一文で示すタグライン、ステータスバッジ。続けて、プロジェクトが解決する課題を平易な 1〜3 文で示す。意図的に行わないこととステータスは、読者の時間を節約できる場合に限り言及する。
- UI、CLI 出力、生成物など見て取れる出力がある場合は、冒頭の直後にスクリーンショットまたは短い GIF を置くこと。
- 使い始め方を示すセクションは 1 つだけ置く。開発者の関与が必要なプロジェクトは `Quick Start`、エンドユーザー向け製品は `Usage`、両方に当てはまる場合は `Usage / Quick Start` とする。セクションの先頭には AI 経路を置く（`AGENTS.md` 経由でリポジトリを AI コーディングエージェントに引き渡す、コピー可能な指示文）。続けて手動の手順を示す。前提条件（ツールチェーン、対応プラットフォーム、固定バージョン）、コピーしてすぐ実行できるコマンド、期待される結果を含めること。エンドユーザー向け製品では、最も一般的な 2〜3 の使い方を期待される出力付きの例で示す。
- Quick Start と Learn More の間には、必要なブロックだけを組み合わせられるショーケース領域を置く。`Concepts` は読者が押さえるべき少数の概念を示す。`Features` は何をするか、なぜ重要か、代替案との相違を示す。`Performance` では性能の主張を一文で示し、それを裏付ける図表または表、計測環境、方法論へのリンクを添える。数字を伴わない性能主張はしない。`Experiments` は実験の内容を示す。ブロックの並び順はプロジェクトが最初に証明したい内容に合わせ、各ブロックには標準的なタイトルと絵文字を 1 つ付ける。
- 詳細ドキュメントへリンクする「目的 → 読むドキュメント」表。
- 明示的に示すライセンス。

セクション見出しには、標準的で短く、読者がすぐ分かる名前を使う。`Quick Start`、`Usage`、`Concepts`、`Features`、`Performance`、`Experiments`、`Learn More`、`License` が基本のセットである。各見出しの先頭には、意味のぶれない絵文字を 1 つ付ける。使い始め方を示すセクションには 🚀、概念には 💡、機能には ✨、性能には ⚡、実験には 🧪、詳しく学ぶセクションには 📚、ライセンスには 📄 を使う。絵文字は少なく統一し、プロジェクトタイトルと本文の文章には使わないこと。

長い補助的内容（プラットフォーム固有のセットアップ、環境変数表、拡張例、トラブルシューティング）は `<details>` ブロックに折りたたむ。`<summary>` は内容を数語で示し、Markdown が正しく描画されるよう直後に空行を 1 つ入れること。重要な部分は決して折りたたまない。冒頭、使い始め方のコマンド、ライセンスは常に展開しておくこと。

読みやすさを保つこと。段落は 1〜3 文とし、箇条書きの各項目には 1 つの内容だけを記載する。コピー可能なコマンドはコードブロックに入れる。列挙は長い文章ではなく、リストか表で示す。詳細ドキュメントと内容が重複しないよう、そちらへ誘導する。チュートリアル、参考資料、解説は詳細ドキュメントのモードであり、README のモードではない。ただし、README を「ドキュメントを参照」の一行だけに縮めてはならない。README だけで入口として機能しなければならない。長さが数画面を超えるようになったら目次を付けること。

古い README は無いより悪い。読者を誤った方向へ導いてしまうからである。セットアップ、使い方、スコープが変わる変更では、README も同じ変更の中で更新すること。開発が停滞または停止した場合は、冒頭で明示すること。

確定したプロダクト/UI の言語ポリシー（[言語ポリシー](language-policy.md)を参照）はエージェント向けである。`AGENTS.md` に記録し、README には記載しないこと。

テンプレート：[README.template.md](../../../templates/README.template.md)

## DEVELOPMENT.md

すべてのプロジェクトに `DEVELOPMENT.md` を含めること。

このドキュメントは利用方法と参考資料を兼ねる。手順に沿ったワークフローを先に示し、コマンドと設定の参考資料を後に置くこと。

次の内容を記載すること。

- 開発ワークフロー
- ツールチェーン
- よく使う mise タスク
- コーディング規約
- テストワークフロー
- ローカル環境のセットアップ
- 検証ワークフロー
- 必要に応じたデプロイワークフロー

人間と AI エージェントの双方が、開発の進め方を理解できるようにすること。

テンプレート：[DEVELOPMENT.template.md](../../../templates/DEVELOPMENT.template.md)

## CONTRIBUTING.md

すべてのプロジェクトに `CONTRIBUTING.md` を含めること。

このドキュメントはコントリビューションの利用方法を説明する。変更を送ってからマージされるまでの手順を順に示し、背景解説の長文は書かないこと。

次の内容を文書化すること。

- コントリビューションにあたっての要件
- 必要に応じた Issue のワークフロー
- プルリクエストのワークフロー
- レビュー要件
- 必須の検証
- コミット規約

AI が生成した、または AI の支援を受けたプルリクエストでは、説明文に次の内容を明確に含めること。

- 変更の目的
- 変更の影響
- 関連する文脈や背景
- 潜在的なリスクや懸念
- 実施したテストまたは検証

GitHub のプルリクエストテンプレートは、これらの要件との同期を保つこと。

テンプレート：[CONTRIBUTING.template.md](../../../templates/CONTRIBUTING.template.md)

## ARCHITECTURE.md

重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` を維持すべきである。

短く、運用に即した内容に保つこと。

このドキュメントの役割は解説である。境界の背後にある理由を示すものであり、網羅的な参考資料ではない。

簡潔な概要、コードベースの大まかな構成（モジュール名を示し、ファイルにはリンクしない）、アーキテクチャの不変条件を含めること。

包括的で理論的なアーキテクチャドキュメントにしてはならない。

主な目的は、意図しないアーキテクチャのドリフトを防ぐことである。

不変条件と ADR の運用は、[アーキテクチャガバナンス](architecture-governance.md)で定義される。

テンプレート：[ARCHITECTURE.template.md](../../../templates/ARCHITECTURE.template.md)
