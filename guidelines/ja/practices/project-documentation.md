# 必須のプロジェクトドキュメント

すべてのプロジェクトは、`AGENTS.md`、`README.md`、`DEVELOPMENT.md`、`CONTRIBUTING.md` を維持しなければならない。重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` も必須とする。出発点として、`templates/` 配下のテンプレートを使用すること。

## AGENTS.md

すべてのプロジェクトは、リポジトリのルートに `AGENTS.md` を置かなければならない。

これはエージェント向けの入口である。コマンド、エンジニアリング標準、リポジトリの構成、境界、確定した言語ポリシー、プロジェクトの規約を記述する。

書き方のルール（記載場所の選択、セクションの順序、サイズ、ネストされたファイル）は、[AGENTS.md の記述規則](agents-file.md)で定める。

テンプレート：[project-agents.template.md](../../../templates/project-agents.template.md)

## README.md

すべてのプロジェクトに `README.md` を含めること。

README はプロジェクトの表玄関であり、急いでいる人間の読者向けに記述する。最初の画面で、プロジェクトが何であるか、どんな課題を解決するか、どう動かすかを示さなければならない。読者は読み込みではなく体験を求めている。説明の前に、動く状態に至る最短経路を示すこと。エージェント向けのルール（エンジニアリング標準、確定した言語ポリシー、プロジェクトの規約）は `AGENTS.md` に記述する（`templates/project-agents.template.md` を参照）。README は、コピー可能な指示文によってリポジトリをエージェントに引き渡す。

本文は、リポジトリのディレクトリ構成ではなく、読者のタスクを中心に構成すること。Why セクションを単独に設けず、次の順序で構成すること。

- 識別ブロック：プロジェクト名、プロジェクトの内容と対象者を一文で示すタグライン、ステータスバッジ。続けて、プロジェクトが解決する課題を平易な 1〜3 文で示す。意図的に行わないこととステータスには、読者の時間を節約できる場合に限り言及する。
- プロジェクトに視覚的な要素（UI、CLI 出力、生成物）がある場合は、冒頭の直後にスクリーンショットまたは短い GIF を置くこと。
- 使い始めのセクションは 1 つだけ設ける。開発者の関与が必要なプロジェクトは `Quick Start`、エンドユーザー向け製品は `Usage`、両方に当てはまる場合は `Usage / Quick Start` とする。セクション内では AI 経路を先に置く（`AGENTS.md` 経由でリポジトリを AI コーディングエージェントに引き渡すコピー可能な指示文）。手動の手順はその後に置く：前提条件（ツールチェーン、対応プラットフォーム、固定バージョン）、コピーしてすぐ実行できるコマンド、期待される結果。エンドユーザー向け製品では、最も一般的な 2〜3 の使い方を期待される出力を伴う例で示す。
- 中核となる概念と機能：読者が押さえるべき少数の概念と、代替案ではなくこのプロジェクトを選ぶ理由。1 項目 1 行とし、使い始めのセクションの後に置く。
- 詳細ドキュメントへリンクする「目的 → 読むドキュメント」表。
- 明示的に示すライセンス。

セクション見出しは標準的で短く、読者が即座に認識できる名前 — `Quick Start`、`Usage`、`Concepts & Features`、`Learn More`、`License` — とし、それぞれに意味の安定した絵文字を 1 つ前置する：使い始めのセクションには 🚀、概念と機能には ✨、発展的な読み物には 📚、ライセンスには 📄。プロジェクトタイトルには識別用の絵文字を最大 1 つ付けることができる。絵文字のセットは小さく一貫させ、本文の文章には絵文字を使わないこと。

長い補助的内容 — プラットフォーム固有のセットアップ、環境変数表、拡張例、トラブルシューティング — は `<details>` ブロックに折りたたみ、`<summary>` は内容を数語で示すこと。Markdown が正しく描画されるよう、`<summary>` の直後に空行を 1 つ入れること。主要な経路は決して折りたたまない — 冒頭、使い始めのコマンド、ライセンスは常に展開しておくこと。

読みやすさを保つこと。段落は 1〜3 文とし、箇条書きの各項目には 1 つの内容だけを記載する。コピー可能なコマンドはコードブロックに入れる。列挙は連続した文章ではなく、リストまたは表で示す。内容を重複して記載せず、詳細ドキュメントへ誘導する。ただし、README を「ドキュメントを参照」の一行だけに縮めてはならない。入口として単独で機能しなければならない。数画面を超える長さになったら目次を付けること。

古い README は存在しないより悪い。読者を積極的に誤解させるためである。セットアップ、使い方、スコープを変える変更では、同じ変更で README を更新すること。開発が停滞または停止した場合は、冒頭で明示すること。

確定したプロダクト/UI の言語ポリシー（[言語ポリシー](language-policy.md)を参照）はエージェント向けである。`AGENTS.md` に記録し、README には記載しないこと。

テンプレート：[README.template.md](../../../templates/README.template.md)

## DEVELOPMENT.md

すべてのプロジェクトに `DEVELOPMENT.md` を含めること。

次の内容を記載すること。

- 開発ワークフロー
- ツールチェーン
- よく使う mise タスク
- コーディング規約
- テストワークフロー
- ローカル環境のセットアップ
- 検証ワークフロー
- 必要に応じたデプロイワークフロー

人間と AI エージェントの双方が、開発の進め方を理解できるようにすること。

テンプレート：[DEVELOPMENT.template.md](../../../templates/DEVELOPMENT.template.md)

## CONTRIBUTING.md

すべてのプロジェクトに `CONTRIBUTING.md` を含めること。

次の内容を文書化すること。

- コントリビューションにあたっての要件
- 必要に応じた Issue のワークフロー
- プルリクエストのワークフロー
- レビュー要件
- 必須の検証
- コミット規約

AI が生成した、または AI の支援を受けたプルリクエストでは、説明文に次の内容を明確に含めること。

- 変更の目的
- 変更の影響
- 関連する文脈や背景
- 潜在的なリスクや懸念
- 実施したテストまたは検証

GitHub のプルリクエストテンプレートは、これらの要件との同期を保つこと。

テンプレート：[CONTRIBUTING.template.md](../../../templates/CONTRIBUTING.template.md)

## ARCHITECTURE.md

重要なアーキテクチャ上の境界を持つプロジェクトでは、`ARCHITECTURE.md` を維持すべきである。

短く、運用に即した内容に保つこと。

簡潔な概要、コードベースの大まかな構成（モジュール名を示し、ファイルにはリンクしない）、アーキテクチャの不変条件を含めること。

包括的で理論的なアーキテクチャドキュメントにしてはならない。

主な目的は、意図しないアーキテクチャのドリフトを防ぐことである。

不変条件と ADR の運用は、[アーキテクチャガバナンス](architecture-governance.md)で定義される。

テンプレート：[ARCHITECTURE.template.md](../../../templates/ARCHITECTURE.template.md)
