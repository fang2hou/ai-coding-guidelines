# テスト戦略

テストは、意味のある振る舞いを検証すべきである。

カバレッジを上げるためだけのテストを書かないこと。

テストを追加する前に、そのテストで検出したい障害モードを理解すること。

優先するのは次の対象である。

- 中核となるビジネスロジック
- 重要なユーザー動作
- 不具合が起きやすいと分かっているパス
- 境界条件
- エラー処理
- 例外的な状況
- 統合の境界

カバレッジの指標は情報を提供するが、カバレッジ率そのものが目的ではない。

目的は、重要な振る舞いが正しく動くという確信を得ることである。

## フロントエンドの E2E テスト

フロントエンドプロジェクトでは、現実的に実行可能な範囲で E2E テストを含めるべきである。

E2E テストの対象は次のとおりである。

- 主要なユーザーフロー
- 重大なプロダクト動作
- 重要な統合動作

現実的なテストデータを優先すること。

本番に近い実データが有用な場合は、適切に匿名化・サニタイズしたものを使用すること。

本番の機密情報をテストフィクスチャに含めてはならない。

E2E テストの実行時間を、管理可能な範囲に保つこと。

それに見合う確信を与えないまま、迅速な検証ワークフロー([品質ゲート](../toolchain/quality-gates.md)を参照)を大幅に遅くする巨大な E2E スイートを作らないこと。

Playwright を使うプロジェクトでは、`eslint-plugin-playwright` を `jsPlugins` 配列から oxlint に読み込む。このプラグインは oxlint の適合性テストの対象として公式にサポートされている。oxlint の JS プラグイン機能は現在アルファ段階である。

`overrides` エントリでルールの適用範囲を Playwright のテストファイルに限定し、アプリケーションコードには適用されないようにすること。

```jsonc
// .oxlintrc.json
{
  "jsPlugins": ["eslint-plugin-playwright"],
  "overrides": [
    {
      "files": ["e2e/**/*.ts"],
      "rules": {
        "playwright/no-networkidle": "error",
        "playwright/no-wait-for-timeout": "warn"
      }
    }
  ]
}
```

## フロントエンドのユニットテスト

フロントエンドプロジェクトでは、現実的に実行可能な範囲で、重要なコンポーネントとロジックのユニットテストを含めるべきである。

テストの品質を高めるのであれば、現実的でサニタイズ済みのデータを使用すること。

優先するのは次の対象である。

- 重要なコンポーネントの振る舞い
- ビジネスロジック
- 状態遷移
- データ変換
- エッジケース
- エラーが発生する条件

ユニットテストを高速に保つこと。

実装の詳細をなぞるだけのテストを避ける。
