# テスト戦略

テストは、意味のある振る舞いを検証すべきである。

カバレッジを増やすことだけを目的にテストを書いてはならない。

テストを追加する前に、そのテストが検出する障害モードを理解すること。

優先するのは次の対象である。

- 中核となるビジネスロジック
- 重要なユーザーの振る舞い
- 障害が発生しやすいことが分かっている経路
- 境界条件
- エラー処理
- 例外的な状況
- 統合の境界

カバレッジ指標から情報は得られるが、カバレッジ率そのものが目的ではない。

目的は、重要な振る舞いが正しく機能するという確信を得ることである。

## フロントエンドの E2E テスト

フロントエンドプロジェクトでは、現実的に実施できる場合は E2E テストを含めるべきである。

E2E テストの対象は次のとおりである。

- 主要なユーザーフロー
- 重要なプロダクトの振る舞い
- 重要な統合の振る舞い

現実的なテストデータを優先すること。

本番環境に近いデータが有用な場合は、適切に匿名化またはサニタイズしたデータを使用すること。

本番環境の機密情報をテストフィクスチャに含めてはならない。

E2E テストの実行時間を抑えること。

相応の確信をもたらさないまま、迅速な検証ワークフロー（[品質ゲート](../toolchain/quality-gates.md)を参照）を大幅に遅らせる巨大な E2E スイートを構築してはならない。

Playwright を使うプロジェクトでは、`jsPlugins` 配列を介して `eslint-plugin-playwright` を oxlint に読み込むこと。このプラグインは oxlint との適合性テストを公式に受けている。oxlint の JS プラグインサポートは現在アルファ版である。

`overrides` エントリでルールの適用範囲を Playwright のテストファイルに限定し、アプリケーションコードに適用されないようにすること。

```jsonc
// .oxlintrc.json
{
  "jsPlugins": ["eslint-plugin-playwright"],
  "overrides": [
    {
      "files": ["e2e/**/*.ts"],
      "rules": {
        "playwright/no-networkidle": "error",
        "playwright/no-wait-for-timeout": "warn",
      },
    },
  ],
}
```

## フロントエンドのユニットテスト

フロントエンドプロジェクトでは、現実的に実施できる場合は、重要なコンポーネントとロジックのユニットテストを含めるべきである。

テストの品質向上に役立つ場合は、現実的でサニタイズ済みのデータを使用すること。

優先するのは次の対象である。

- 重要なコンポーネントの振る舞い
- ビジネスロジック
- 状態遷移
- データ変換
- エッジケース
- エラーが発生する条件

ユニットテストは高速に保つこと。

実装の詳細をそのまま再現するだけのテストを避けること。
