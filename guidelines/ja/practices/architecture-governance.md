# アーキテクチャガバナンス

## アーキテクチャの不変条件

プロジェクトは、AI エージェントが誤って破ってはならないアーキテクチャ上の制約を、明示的に記録すべきである。

現在のアーキテクチャの境界と不変条件を記録するには、`ARCHITECTURE.md` を使用すること。

例として、次のようなものがある。

- ドメインロジックを担うレイヤー
- 外部 API を呼び出せるモジュール
- 認証の境界
- 状態管理の境界
- Databricks へのアクセス境界
- フロントエンドとバックエンドの責務
- 依存関係の方向
- 統合の境界

この文書は簡潔に保つこと。

次の問いに答えるものでなければならない。

> **現在のアーキテクチャで、何を維持しなければならないか。**

この文書をいつ必須とするかは、[必須のプロジェクトドキュメント](project-documentation.md)で定める。

## アーキテクチャ決定記録

重要なアーキテクチャ上の決定には、ADR を使用すること。

重要なアーキテクチャ上の決定は、一貫した構成の ADR として個別に記録すること。

ADR には、次の事項を記載すること。

- 背景
- 決定
- 検討した代替案
- 判断の理由
- 帰結

この構成には、共通の [ADR テンプレート](../../../templates/adr.template.md)を使用すること。

ADR は不変の規則ではない。

ADR はアーキテクチャのガードレールとして機能し、特に AI エージェントによるコードベースの変更時に、意図しない変更を防ぐのに役立つ。

ユーザーの要求が ADR と競合する場合は、次の手順で対応すること。

1. ユーザーの実際の意図を理解する。
2. その ADR が存在する理由を理解する。
3. 決定を変更した場合の影響を評価する。
4. 合理的であれば、既存のアーキテクチャと両立する解決策を優先する。
5. アーキテクチャを本当に変更する必要がある場合は、その影響を説明する。
6. ADR を明示的に更新するか、新しい ADR で置き換える。

ADR に黙って違反してはならない。

アーキテクチャを変更すべきかどうかユーザーが確信を持てない場合は、変更する前に、影響を分析するのを支援すること。
