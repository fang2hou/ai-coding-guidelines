# アーキテクチャガバナンス

## アーキテクチャの不変条件

プロジェクトは、AI エージェントが誤って違反することのないよう、アーキテクチャ上の制約を明示的に記録すべきである。

現在のアーキテクチャの境界と不変条件には、`ARCHITECTURE.md` を使用すること。

例えば次のようなものである。

- どのレイヤーがドメインロジックを担うか
- どのモジュールが外部 API を呼び出せるか
- 認証の境界
- 状態管理の境界
- Databricks へのアクセス境界
- フロントエンドとバックエンドの責務
- 依存の方向
- 統合の境界

このドキュメントは簡潔に保つこと。

次の問いに答えるものでなければならない。

> **現在のアーキテクチャにおいて、何が真であり続けなければならないか。**

このドキュメントがいつ必要になるかは、[必須プロジェクトドキュメント](project-documentation.md)で定義される。

## アーキテクチャ決定記録

重要なアーキテクチャ上の決定には、ADR を使用すること。

重要な決定ごとに、一貫した構造の ADR として個別に保存すべきである。

ADR には、次の事項を記述する。

- 背景
- 決定
- 検討した代替案
- 判断の理由
- 帰結

この構造には、共通の [ADR テンプレート](../../../templates/adr.template.md)を使用すること。

ADR は不変のルールではない。

ADR はアーキテクチャのガードレールとして、特に AI エージェントがコードベースを変更するときに偶発的な変更を防ぐ。

ユーザーの要求が ADR と競合する場合は、次の手順で扱う。

1. ユーザーの真の意図を理解する。
2. その ADR が存在する理由を理解する。
3. 決定を変更した場合の影響を評価する。
4. 合理的であれば、既存のアーキテクチャと両立する解決策を優先する。
5. アーキテクチャを本当に変更する必要がある場合は、その影響を説明する。
6. ADR を明示的に更新するか、新たな ADR で置き換える。

ADR を黙って違反しないこと。

アーキテクチャを変更すべきかどうかユーザーが確信を持てない場合は、変更する前に帰結の分析を支援すること。
