# Rust ツールチェーン

## 適用義務

TypeScript と Python は AI 支援開発のデフォルト言語である。ライブラリとエージェントのエコシステム支援が最も充実しているためである。

Rust はデフォルトの選択肢ではない。

次の要件が本当に必要な場合にのみ Rust を選ぶ。

* メモリ安全性を保ちながらの最大性能
* システムコンポーネント
* 他言語から呼び出すネイティブ拡張
* WebAssembly ターゲット

Rust の採用には明確な理由とユーザーの承認が必要であり、プロジェクトの ADR に記録する。

Rust に慣れていること自体は理由にならない。

## 適用範囲

これはベースラインであり、採用前にプロジェクト個別の分析を行う。

採用前に、要件が上記の場面のいずれかに該当すること、そして TypeScript・Python・Go のいずれでも許容できるコストで満たせないことを確認する。

## バージョン方針

stable ツールチェーンを mise または rustup でインストールして使う。

`Cargo.toml` は edition 2024 を使う。

nightly の機能はデフォルトで有効にしない。nightly が必要な場合は、明示的な決定として記録する。

## 利用ルール

### ビルドとパッケージング

ビルドとパッケージングには `cargo` だけを使う。

標準の cargo コマンドを独自のビルドスクリプトの裏に隠さない。

### フォーマット

フォーマットには `rustfmt` を使う。

`cargo fmt` を mise タスクとして公開する。

### リント

リントには `cargo clippy` を使う。

CI では警告をエラーとして扱う。

```bash
cargo clippy --all-targets -- -D warnings
```

### unsafe ブロック

すべての `unsafe` ブロックには `// SAFETY:` コメントを付け、そのブロックが安全である根拠となる不変条件を説明する。

借用チェッカーを回避する目的で `unsafe` を使わない。

### エラー処理

ライブラリのエラー型には `thiserror` を使う。

`anyhow` はバイナリの境界でのみ使う。ライブラリの公開 API に漏らさない。

### ワークスペース構成

複数クレートのプロジェクトでは cargo ワークスペースを使う。

依存関係のバージョンはワークスペースレベルで同期する。

### テスト

CI では `cargo test` を実行する。
