# shadcn/ui

## 判定

推奨 — Tailwind ベースのアプリケーションでは、shadcn/ui を第一候補のコンポーネントシステムとする。

## 使用する場面

- UI コンポーネントが必要な Tailwind ベースのアプリケーションを構築する場合。
- ユーザーが別のコンポーネントライブラリやバージョンを明示的に要求していない新規プロジェクト。

## 避けるべき場面

- ユーザーが別のコンポーネントライブラリやバージョンを明示的に要求した場合 — その要求に従う。
- プロジェクトが Tailwind CSS を使っていない場合。shadcn/ui は Tailwind ベースのアプリケーション向けコンポーネントシステムである。

## 長所

- コンポーネントはソースコードとしてリポジトリにコピーされるため、内容をすべて確認・調整できる。
- 開発・保守コストを抑えられる。見た目の不統一、アップグレード時の競合、AI が生成したコンポーネントの重複も避けられる。
- 公式のバリアントと設定機構により、コンポーネント内部を編集せずに、ほとんどのカスタマイズに対応できる。

## トレードオフ

- コピーしたコンポーネントはアップストリームから乖離する可能性があり、内部を改変するとアップグレードリスクが生じる。
- コンポーネントを公式実装に近い状態で保つには、規律ある運用が必要である。

## バージョン方針

- 新規プロジェクトでは、適用可能な最新の shadcn/ui セットアップを優先する。
- ユーザーが別のコンポーネントライブラリやバージョンを明示的に要求した場合は、その要求に従う。

## 利用ルール

- プロジェクトのセットアップでは、shadcn/ui の公式ドキュメントに従う。

### プリミティブ層（Radix / Base UI / React Aria）

- shadcn/ui の各コンポーネントは、複数のプリミティブ層で提供される。Base UI は 2026 年 7 月以降、アップストリーム側のデフォルトであり、本ガイドラインでもこの層を推奨する。Radix と React Aria も引き続き利用できる。
- 新規プロジェクトではデフォルトの Base UI 層を使う。ユーザーの明示的な要求なしに、Radix や React Aria に切り替えてはならない。
- 既存の Radix プロジェクトでは Radix を維持する。移行は任意であり、必須ではない。移行はユーザーの明示的な要求がある場合に限り、公式の移行スキルを使い、コンポーネント単位で行う。

### コンポーネントのパスと構成

- shadcn/ui のコンポーネントは `components/ui` にインストールし、そのままそこに置く。このパスはアップストリームが所有する。
- アプリケーション独自のコンポーネントは、同じ `components/` 配下で Atomic Design Methodology に沿ってサブディレクトリに整理する：`atoms/`、`molecules/`、`organisms/`。アプリに必要なら `templates/` と `pages/` も加える。
- カスタムコンポーネントを `components/ui` に置いてはならない。アップストリームのツリーとファーストパーティコードを分離しておく。

構成例：

```text
components/
  ui/            # shadcn/ui — upstream-owned
    button.tsx
    dialog.tsx
  atoms/
    price-tag.tsx
  molecules/
    search-field.tsx
  organisms/
    product-table.tsx
```

### コンポーネントの再利用

- 合理的な範囲で、shadcn/ui コンポーネントをできるだけ使う。
- カスタムコンポーネントを作る前に、shadcn/ui が適切なプリミティブやコンポーネントをすでに提供していないか確認する。
- 不要な自作実装より、既存コンポーネント、既存コンポーネントの組み合わせ、公式バリアント、公式の設定機構を優先する。
- 目的は、開発・保守コストを抑え、見た目の不統一、アップグレード時の競合、AI が生成したコンポーネントの重複を減らすことである。

### 不要な改変を避ける

- ダウンロードしたコンポーネントは、公式実装に近い状態で保つ。
- テーマ変数、Tailwind 設定、コンポジション、既存コンポーネントの API、標準バリアント、ラッパーコンポーネント、サポート対象のデザイントークンで実現できる変更については、コンポーネント内部を改変してはならない。
- プライマリカラー、テーマ設定、タイポグラフィ、Markdown レンダリング、フォントサイズ、コンポーネントのバリアントなどを変更する場合は、コンポーネント内部を直接編集する前に、shadcn/ui と関連する Tailwind の公式ドキュメントを確認する。

### 必須のオーバーライドを文書化する

- ダウンロードしたコンポーネントに内部の改変が本当に必要な場合は、変更したコンポーネント、変更内容、変更が必要な理由、その改変によって生じるアップグレードリスクを記録する。
- この情報はリポジトリ内の Markdown ドキュメントに残す。将来の開発者や AI エージェントが shadcn/ui のアップグレード時に、この差異を把握できるようにするためである。

### ダウンロード済みコンポーネントの除外

- `components/ui` はアップストリームから取り込んだソースであり、ファーストパーティコードではない。`components/ui` を `oxlint` と `oxfmt` の対象から除外し、ツールの出力をプロジェクトが所有するコードに絞る。
- `.oxlintrc.json` と `.oxfmtrc.json` の `ignorePatterns` に `components/ui/**` を追加する。両ツールとも、独立した ignore ファイルではなく、設定ファイル内の `ignorePatterns` を推奨している。この除外により、アップグレード時の差分にリントやフォーマットによる変更が混入しなくなる。

```json
{ "ignorePatterns": ["components/ui/**"] }
```

### ツール連携（MCP または CLI）

- コンポーネントの追加と更新は shadcn CLI または shadcn MCP ツールで行う。ツールが利用できる場合、コンポーネントファイルを手作業でコピーしてはならない。
- 開発環境が MCP に対応している場合は、公式の shadcn MCP 統合を優先する。同じツールで、`components.json` に設定された shadcn 互換レジストリも扱える。
- MCP 対応環境でユーザーが shadcn/ui を使っており、MCP 統合が未設定であれば、エージェントはその設定を支援してよい。
- コンポーネントがローカルにすでに存在する可能性がある場合は、`--dry-run` または `--diff` でプレビューする。
